# AGENTS.md — DroneFlames PC port

Працюй українською як відповідальний співрозробник Godot/GDScript. Зберігай мову, імена й стиль файлів. ZaGOR-1 координує роботу й ухвалює stable/release рішення. OKREDU — співавтор, Codex — основний агент, Gemini — для узгоджених ізольованих задач. Зберігай авторство та provenance. Репозиторій почато з нового snapshot. Старі гілки, PR і ancestry не відновлюй.

## Початок сесії

1. Прочитай цей файл і [PROJECT_STATE.md](docs/PROJECT_STATE.md). Звір Git root, branch, HEAD, status і worktrees. Перед стартом нової гілки перевір погоджений tip `beta` та за потреби remote refs.
2. Визнач scope й критерії перевірки. Через [INDEX.md](docs/INDEX.md) відкрий лише документи за темою. Звір код, прямі залежності, контракти та тести. Для великих файлів і логів використовуй пошук і потрібні діапазони.
3. Фактичний source і тести визначають поведінку в перевіреному scope. Git визначає refs, власник — дозволи. Успадковуй докази за збігу коду, runtime, PCK, fixtures, конфігурації, середовища й сценарію. Назва `verified` не робить історичний PASS чинним.

## Пріоритети та зміни

- Ціль — Windows x64, стабільний portable `DroneFlames.exe`, фізичний GUI/LAN/Steam QA, усунення native crashes і падіння до 2–3 FPS у late-game. Linux native і cross-play відкладені до окремої задачі. Нові gameplay-функції, великий UI redesign і стороння 0.41.x потребують прямого запиту. Сторонні матеріали використовуй лише з відповідними правами.
- Покращуй архітектуру поетапно. Clean Architecture, SOLID, DRY, KISS, YAGNI й data-oriented design застосовуй до доведеної потреби. Спочатку characterization/regression tests, потім вузька зміна. Уникай регресій заради рефакторингу.
- Профілюй важкі бої на Windows. Орієнтири — 30+ FPS у визначеному важкому сценарії та 60 FPS у звичайному. Для performance/architecture PR виконай baseline → доказ bottleneck → малий PoC → цільові тести й парний benchmark → QA після GO → review. Spatial hashing, MultiMesh, pooling, typed GDScript та GDExtension розглядай як гіпотези до вимірів. Використовуй тільки [Real-World Gaming Profile B](docs/performance.md#real-world-gaming-profile-b), зберігай усі пари та фіксуй сторонній CPU. Якщо фон заважає висновку, став INCONCLUSIVE. Headless CPU, GUI FPS і фізичний Windows QA мають різні межі. Камера й visual culling не керують симуляцією.

## Git і повноваження

- `main` — стабільна база, `beta` — інтеграція та QA. Тематичний worktree створюй від погодженої `beta` у `~/projects/droneflames-worktrees/`. Бережи чужі зміни й shared/OKREDU гілки. Уникай руйнівних `reset --hard` і `git clean`.
- Після завершеного етапу та перевірок створи локальний Conventional Commit. Переглянь повний diff, staged files, status, тести й секрети. Додавай файли явно. Зберігай унікальні коміти, локальні дельти та докази, включно з NO-GO, в канонічному handoff. Прибирай тимчасові worktrees і гілки після інтеграції, перевірки відновлення й дозволу власника.
- Push тематичної гілки та створення PR дозволені в межах узгодженого GitHub workflow. Дозволи попередніх задач не переносяться. Прямі коміти й push у `main`/`beta`, merge, force push, rebase чи інше переписування опублікованої історії, workflow dispatch, теги, релізи, публікація production artifacts і видалення гілок потребують окремого прямого дозволу. Інтеграція через PR, для `beta → main` потрібні acceptance QA та рішення власника. Порядок перевірок, Draft PR, review і branch protection описано в [Development Workflow](docs/DEVELOPMENT_WORKFLOW.md).
- Не коміть credentials, токени, `account.bin`, rejoin seats, Steam secrets, приватні dumps, кеші або тимчасові збірки. Публічний доступ не надає прав на розповсюдження коду чи графіки.

## Godot, сумісність і Windows QA

- `game/project.binary` + `game/override.cfg` штатні. Не створюй `game/project.godot`. Не видаляй, не untrack і не ігноруй глобально `game/.godot/`, там потрібні binary scenes та imports. Editor, import і генерацію UID/cache запускай лише у фізичній копії. `.import` з кінцевим NUL може бути mapping. Звір editor, template, source і toolchain за [build guide](docs/codex/verified/BUILD_RELEASE.md). Перед зміною `class_name`, сигналів, node paths, RPC чи enum ordinals перевір залежності й сумісність.
- Authoritative simulation незалежна від FPS, камери, visibility та wall-clock. Зберігай RNG draws, ID, host command order, fixed MP ticks, маршрути та snapshot state. Обґрунтовуй authoritative вплив змін порядку обходу й кешів. Для змін перевір same-seed replay, NetHash, Save/Load, repeated restore та host/peer. MP UI commands ідуть через `NetSession` із host authorization та schema/wire validation. Додай негативні сценарії. Host migration потребує фактичної реалізації.
- Legacy saves мають читатися. Downgrade не гарантовано. Зберігай defaults для відсутніх `sys.diplo.land_cooldowns` і `sys.hold.far_fail` як порожні дані, незалежність Navy від незбережених TTL, freeze snapshot перед autosave worker і очищення stale state. Failed restore не має видавати успіху чи просувати turn. Контракти та fixtures у [Multiplayer](docs/codex/verified/MULTIPLAYER_PROTOCOL.md) і [Save format](docs/codex/verified/SAVE_FORMAT.md).
- `game/pc/version.cfg` визначає номер, `Menus.VERSION` синхронізовано з префіксом v. Docs, tooling, тести й PoC самі по собі не підвищують версію. PROTO, SIM_REV та Save.FORMAT змінюй лише за погодженням. Перед інтеграцією застосуй [Versioning Policy](docs/VERSIONING_POLICY.md).
- One-file SFX містить runtime/PCK і розпаковує DLL у приватний versioned cache. Для two-peer QA зберігай portable ZIP з EXE і трьома DLL. Зміни DLL потребують дозволу та перевірки provenance і ліцензій. Steam AppID 480 тестовий. Використовуй один точний EXE/DLL комплект із однаковими SHA256, ізолюй профілі, вимикай updater через `DF_NO_UPDATE=1` і `--repo ""`. Межі SFX, MinGW, CI й фізичного QA наведено в [Windows QA](docs/WINDOWS_QA.md).

## Тести, локалізація і завершення

- Виконуй цільові тести за scope. Повну релевантну матрицю запускай перед інтеграцією, релізом або за високого ризику. CI, headless, Wine і фізичний Windows підтверджують власні сценарії. Фіксуй PASS, FAIL, SKIP, NOT RUN або N/A та точні умови. Не послаблюй assertions заради економії часу. [Команди та MCP](docs/DEVELOPMENT_WORKFLOW.md#перевірки-за-scope)
- Для користувацьких рядків використовуй Loc, TranslationServer і PO. Перекладай шаблон до підстановки, застосовуй `Loc.mk` для повторного рендера. Публічні ru/uk/en мають спільні активні ключі, стабільні контексти, непорожні переклади й відповідні placeholders без дублювання. Винятки на кшталт двомовного першого запуску обґрунтовуй. ru використовує вихідний текст, es — прихована beta. Відокремлюй власні назви, команди та ключі даних від UI. Імена гравців, версії та службові значення не використовуй як translation keys. Локалізація зберігає authoritative state, RNG, ID, saves і wire keys. Зміна архітектури локалізації потребує обґрунтування, перевірки preferences і документації. Після змін запусти `python3 tools/check_l10n.py`, релевантні тести й перевір відповідні екрани ru/uk/en, діалоги, tooltips, розмір і повторне відкриття.
- Вибирай MCP за задачею. Перевір шлях і свіжість shadow перед висновками, редагуй лише правильний worktree. Локальну конфігурацію й credentials не публікуй. Не встановлюй Godot editor addon у production без дозволу. [Матриця MCP](docs/DEVELOPMENT_WORKFLOW.md#вибір-mcp)
- Після суттєвої роботи онови зачеплені канонічні документи й короткий PROJECT_STATE з точним baseline, handoff, результатами, обмеженнями й наступним кроком. Сирі дані зберігай окремо. Історичні звіти зберігай з датою, джерелом і межами. Для дрібних дій окремий звіт не потрібний.
