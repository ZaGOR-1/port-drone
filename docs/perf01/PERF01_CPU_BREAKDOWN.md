# PERF-01. CPU за стадіями

Заміри монотонного часу навколо викликів у GDScript включають вкладені виклики. `missile_multi_plan` усередині `_missile_tap` або `StrikeSheet.refresh` наведено окремо для локалізації витрат. Витрати незалежних draw callbacks агреговано як render prep.

- Відкриття A → B зайняло 2.21 → 2.17 мс. Кількість Control після відкриття і на 500 цілях у контрольній парі становила 900 на варіант.
- На 500 цілях StrikeSheet.refresh коштував 28.85 → 19.86 мс/кадр, усі копії `_plan_targets` — 3.15 → 2.23 мс/кадр. Повний preview-план викликався 13.0 → 9.0 разів на 26 кадрів. У B в одному кадрі виконується менша частка періодичних preview-викликів завдяки вищій частоті кадрів.
- Підтвердження 500 цілей коштувало 105.22 → 107.18 мс. StrikeHub формує повний план для ETA, далі launch_missiles_multi повторює планування перед заповненням черги. Кожен варіант викликав планувальник двічі.
- Медіана `_update_tels` у 105 кроках 0.327 → 0.335 мс, усього кроку 0.55 → 0.51 мс. Після 105 кроків активні 250 ракет; середній кадр на цьому стані 41.83 → 43.15 мс. Симуляція після серії кроків знову стояла.

Поріг у 200 відсутній у перевіреному коді й замірах. До виправлення клік повторював планування N цілей за T готових установок. За сталої кількості установок це приблизно лінійне зростання на один клік та сумарно квадратична робота за серію кліків. Hit-testing також лінійний на клік та значно дешевший за план. Сортування в `tels_for` у цьому навантаженні відсутнє, бо обидва варіанти призначили всі 500 ракет.

Залишкові витрати зосереджені в періодичному preview та в повторній повній побудові плану при підтвердженні. Їхнє профілювання на Windows має пріоритет після повторної QA.
