# PERF-01. Масовий вибір цілей ОТРК

База `beta` — `c91e0e6a7eef831687e6e63550560bba739a6b87`. Початковий Windows-звіт прив’язано до PR #7 ZIP із revision `0e8316ee167b11a90925e33a126290b6848d9986`, SHA256 `883668885c8f75e882b17b9330bbaac0e34c16e240c14da3e5f739eb1e3674c1`. У цих ревізіях збігаються реалізації вибору, планувальника, StrikeSheet і обох оверлеїв. Різниця в Main і NetSession стосується рядків інтерфейсу. PR #8 змінює обробку вводу в Main і не входить до кандидата.

| Стадія | Фактичний шлях |
| --- | --- |
| Відкриття | Дія HUD `missile` → `strike_open("tel")` → `_strike_enter` під’єднує StrikeSheet та StrikeMarks. |
| Вибір | Viewport mouse → `_unhandled_input` → `_release_press` → `_tap` → `_missile_tap` → `_plan_tap`. Попередні точки в `plan_list`, поточна точка й лічильник у `plan_target` і `plan_count`. Клік по старій точці збільшує її лічильник, нова точка додається в кінець. |
| Hit-testing | `_plan_hit` перевіряє активну ціль. `_plan_tap` сканує попередні цілі в екранних координатах із радіусом 22 px. `_on_plan_point` перевіряє також попередні цілі, коли спрацьовує гілка близьких послідовних кліків. |
| HUD і hover | StrikeSheet має фіксовані елементи, відображає боєзапас, призначення, ETA і застереження. Зміна кількості точок або ракет одразу оновлює план. У стані спокою план оновлюється з інтервалом 0,25 с за `delta`. `_pc_hover_ui` перевіряє стан viewport і HUD, а не всі цілі. |

Базовий клік виконував `missile_multi_plan` тільки заради поля `available`. Планувальник для кожної запитаної ракети обирає установку з найбільшим залишком, а за рівності з найменшою дистанцією. Це повторний прохід по установках для кожної цілі. За браку призначень перевірка причини може додатково викликати `tels_for` із сортуванням. На виміряному шляху призначення пройшли для всіх цілей, тому сортування не було причиною затримки.

Суміжне навантаження створювали 12 примітивів у кожному статичному `PathKit.reticle`. Кандидат зберігає статичну форму у текстурі, запеченій із цього самого малювання. Активний приціл і його анімація, порядок міток, підписи, піктограми та траєкторія використовують чинні шляхи малювання. Клік ОТРК тепер використовує `missiles_ready` з тим самим набором умов по власнику, стану установки і черзі. Фактичне призначення та підтвердження використовують повний планувальник. Порівняння статичного прицілу на трьох фонах дало максимальну різницю RGB 2/255 на llvmpipe.

Підсистема ОТРК працює в GDScript. Нативні залежності в цьому сценарії обмежені Godot, рендерером і загальними платформними GDExtension. GodotSteam і WebRTC стосуються транспорту, а df_device не бере участі у виборі та малюванні цілей.
