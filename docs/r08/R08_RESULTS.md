## Причина піка

Сценарій відтворився. Перший headless профіль із вузькими scopes дав 159,66 мс inclusive у чотирьох викликах `NetSession._exec`. У основному GUI профілі їхня медіана становила 174,29 мс. Усі чотири команди — `call army.order_attack`, по 188 байтів `var_to_bytes(cmd)` на команду. Виклики застосовано в порядку slot 0, 1, 2, 3, на тику 4692, turn 1564, exec_tick 0, перед simulation tick 4693. Витрати нижче — медіани трьох GUI-прогонів кожного варіанта. У світі було 1015 юнітів на початку команд.

| --- | ---: | ---: | ---: | ---: |
| 0 → 3 | 180 | 0 × 204 | 3,398 → 3,515 | 0 → 0 |
| 1 → 0 | 200 | 200 × 74 | 40,397 → 28,453 | 18,507 → 6,838 |
| 2 → 8 | 0 | 0 | 0,268 → 0,370 | 0 → 0 |
| 3 → 5 | 359 | 359 × 120 | 130,050 → 89,455 | 69,321 → 25,623 |

`Army.order_attack` відбирає армії, пробує tactical start для груп, будує спільний маршрут і для fallback-юнітів зсуває кожну точку через `Army.safe_point`. Друга й четверта команди зробили 14 800 та 43 080 викликів `safe_point`. З них 1 587 та 4 754 виклики потребували `Economy.land_point`. У детальному аудиті вони охопили відповідно 609 та 2 130 різних ключів клітинки й радіуса. Отже, 978 та 2 624 запити повторювали ключ. Однаковий ключ може мати різні дробові координати fallback. Попередня команда також змінює шляхи, прапорці операцій і стан армій. Кандидат не зберігає результатів запитів.

У GUI на `_exec` поза `callv` припало 0,106 → 0,143 мс. Тут враховано валідацію, іншу обробку та локальне вимірювання. Валідація окремих команд займала десятки мкс, різниця між вкладеними `callv` і `order_attack` — переважно одиниці мкс. У другій та четвертій командах було 17 та 34 бюджетних `army_path` виклики і по одному `nav_path`. Медіана `nav_path` для найдорожчої команди становила 1,316 → 1,361 мс. Під час тика після пакета `Army.update` і `Operations.update` займають близько 8–9 та 3 мс у контрольній парі. У детальному headless профілі `safe_point` сумарно 161,09 → 108,56 мс включно з `land_point`. Повідомлення `say` зайняли 0,071 → 0,128 мс. Ці вкладені scopes не додаються до батьківських. У циклі формування fallback-шляхів немає явного сортування, створюється окремий packed path для кожного юніта. Нативні heap allocations і внутрішні підскоупи AStar мають статус NOT RUN.

Старий `land_point` для кожного радіуса обходив квадрат, відкидаючи його внутрішні клітинки, і окремо викликав перевірку меж та читання біому. B обрізає рядки до меж карти й перебирає тільки периметр у тому самому порядку. Горизонтальні краї йдуть зліва направо, проміжні рядки перевіряють спочатку ліву, потім праву клітинку. Читання `biomes[y * w + x]` відповідає `WorldData.get_biome`. Міст у вихідній клітинці, перевірка лише біому для кандидата, рівність, радіус і повернення вихідної дробової точки збережені. Для повного кільця радіуса r цикл відвідує 8r клітинок замість перевірки (2r+1)² позицій. Це єдина зміна в ігровому коді.
