# R33 · Критерії до вимірювань

База `acd9760`, 0.36.11. [R30](../r30/R30_RESULTS.md#3-army--застосовувати-шкоду-до-вже-знайденої-клітини-укріплення) · [Profile B](../performance.md#real-world-gaming-profile-b)

## Дешевий screen

Rendered replay на базі змішаних армій R23, seed 20261016, Vulkan Mobile 1280×720, fixed camera та 30 Hz simulation. Важкий D2100 із трьома активними фронтами та C1200 з укріпленнями на одному. Перед запуском поставити рядами штатні `build_line` на належних захиснику сухих клітинах. У кожного контакту свій ряд і кілька смуг руху, змішані unit types, чинні стрільба, навігація, HP, руйнування та wire orders. Після setup жодних телепортів, відновлення HP чи підміни сканування. Перші 150 тіків від старту фіксують прихід і прорив першої хвилі. У репрезентативному важкому screen потрібні контакти щонайменше на двох фронтах, hard/soft scan і руйнування щонайменше на одному. В іншому разі уточнити fixture без зміни порогів або вказати INCONCLUSIVE.

Знімати inclusive `_advance` і лише nearest loop з виклику crush, окремо від HP, remove, навігації та callbacks. Зберегти за tick кількість викликів, довжини сканів, hard/soft, збіг очікуваної клітини, ruin і кількість контактів за фронтами. Для кожного тика з контактами й для повного вікна показати CPU. Нульова плата guard і усунення всього nearest loop задають оптимістичний бюджет. Для потенційного GO потрібні обидва пороги **≥1 мс/тік і ≥5% inclusive `_advance`** на середньому по всьому важкому вікну після витрат. Для переходу до PoC над порогами потрібен запас, достатній для перевірки membership, fallback, таймера і розкиду. Пікові та contact-only значення показати окремо. За меншим навіть оптимістичним бюджетом — NO-GO, runtime PoC і парний A/B не запускаються.

## Умовне приймання PoC

До A/B потрібні exact cell, HP, порядок `forts_changed`, RNG, NetHash, pending/ownership, навігація, restore й host/peer. Adversarial включає stale mapping, відсутній HP, tie довільної точки, зміни сусідньої клітини через callback і руйнування між двома контактами. Загальний damage API зберігає поведінку.

За PASS провести **4 пари** важкого й **2 пари** легкого сценарію, AB/BA/AB/BA та BA/AB відповідно, з тим самим fixture та вікном. Рахувати парні абсолютні й відносні зміни, медіану та min/max. У heavy потрібні **≥1 мс/тік і ≥5%** чистої економії inclusive `_advance`. У кожному сценарії guard **5%** у несприятливому напрямку для tick p99, frame p99, FPS, 1% low, RSS та VRAM. Звіт з усіма плечима, p50/p95/p99/max, CPU, командним потоком, runnable wait, фоновим CPU і memory PSI. За неможливості атрибуції — INCONCLUSIVE.
