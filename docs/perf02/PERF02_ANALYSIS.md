# PERF-02. Затримка підтвердження ОТРК

База A — PERF-01 `6748e3e` з PR #9. Версія обох варіантів `0.36.1`. У першому контрольному прогоні A клік по кнопці для 500 цілей зайняв 109,16 мс. Два виклики `missile_multi_plan` тривали 52,55 і 53,21 мс. Перший створює призначення для розрахунку ETA, другий створює таке саме призначення перед заповненням черг.

- Кнопка StrikeSheet передає підтвердження до `Main.strike_fire`, де збираються зафіксовані та поточні цілі. В SP Hub викликається синхронно. У MP UI кодує `cmd_strike` і ставить її в чергу. Хост декодує команду, перевіряє відправника й застосовує її до першого кроку відповідного turn.
- `missile_multi_plan` бере готовий боєзапас із живих нерухомих установок потрібної країни, нормалізує кількість ракет на ціль, перевіряє дипломатичні обмеження і дальність та обирає установку. Призначення резервується через `Facility.queued`. Повідомлення, облік залпу, закриття StrikeSheet і очищення вибору використовують ті самі функції.
- Для залпу лише ОТРК між розрахунком ETA й запуском немає іншого озброєння або кроку симуляції. ETA тільки читає призначення. Hub передає готовий план на застосування в межах того самого виклику. Змішані удари, відкладені пуски й прямий виклик `launch_missiles_multi` заново валідують актуальну готовність перед застосуванням. Допоміжне застосування плану не входить до allowlist мережевих команд.

## Preview

Періодичність StrikeSheet лишається 0,25 с, зі штатним негайним оновленням при зміні кількості цілей або ракет. Окремі кадри оновлюють підписи, ETA, застереження, траєкторію активної цілі та маркери. Час одного повного preview зменшено у спільному планувальнику. Він один раз читає позиції й готовність пускових, а потім використовує їх у циклі призначення. Порядок кандидатів береться з того самого словника готовності. Однаковий боєзапас й однакова відстань залишають першу установку в порядку масиву. Дипломатична перевірка й пояснення для недоступних цілей виконуються на кожному повному плануванні.

Дані готовності живуть лише до повернення з функції. Наступний preview і фактичне підтвердження отримують свіжі позиції, власника, стан установок і цілей. Для результату між кадрами довелося б враховувати щонайменше порядок, координати й кількість цілей, дальність, пересування, власників, запас і черги, дипломатію, правила території та стан світу. Збережено чинний інтервал, оскільки скорочення вартості окремого виклику дало вимірюваний виграш. Текстура прицілу PERF-01 використовується при зміні камери, viewport і масштабу.

## Що витрачає час у preview

Медіана двох GUI-прогонів при 500 цілях. `Hub.plan` і `_set_txt` вкладені в `refresh`, а `_arc` — у малювання оверлею. Значення в рядках описують окремі scopes.

| Scope | Викликів на 26 кадрів A → B | Inclusive мс/кадр A → B |
| --- | ---: | ---: |
| `refresh` | 26 → 26 | 20.519 → 6.856 |
| `plan` | 9 → 9 | 17.832 → 4.187 |
| `_set_txt` | 494 → 494 | 0.011 → 0.012 |
| `missile_plan` | 26 → 26 | 0.605 → 0.603 |
| `route_overlay_draw` | 26 → 26 | 5.177 → 5.553 |
| `_arc` | 26 → 26 | 0.096 → 0.101 |
| `strike_marks_draw` | 26 → 26 | 7.740 → 8.050 |

Тривалість повного preview впала при тій самій кількості викликів. Малювання траєкторії та маркерів залишається окремою витратою.

У парі зі зменшенням запасу з 500 до 420 ракет підтвердження зайняло 219,7 → 91,1 мс. У B 80 викликів `tels_for` коштували 76,8 мс, оскільки для непризначених цілей будується відсортований список лише заради пояснення. Це окремий профіль навантаження для наступної перевірки.
