# PERF-03. Підтвердження удару ОТРК при дефіциті ракет

База A — `beta` `11380ee014cae95c1bdc2367b0ee9a1b8cbfed7b`. Для B використано гілку `perf/otrk-ammo-shortage` у `/home/zagor/projects/port-drone-perf03`. Версія обох збірок — `0.36.1`.

На A для кожної цілі, яка отримала менше ракет, ніж замовлено, планувальник викликає `tels_for`. Цей виклик обходить усі установки, перевіряє дальність і сортує придатні за відстанню. Планувальник використовує тільки ознаку порожнього списку, щоб розрізнити «Вне дальности ОТРК» і «Не хватает ракет».

На B перша така ціль ініціалізує масив координат придатних установок на час одного планування. Для кожної недоукомплектованої цілі перевірка завершується на першій координаті в допустимому діапазоні. До масиву входять порожні придатні установки, оскільки вони визначають причину відмови. Перевірка зберігає межі мінімальної та максимальної дальності й фільтри власника, стану установки, пересування та консервації. Дипломатична валідація передує розподілу та поясненням. Для інших викликів `tels_for` повертає відсортований список.

На 500/420 усі три пари показали прискорення. Сортування займало 51,72 мс, а формування пояснень разом із сортуванням — 71,25 мс із 83,49 мс планувальника. Після зміни пояснення займають 0,44 мс. При дефіциті однієї ракети пояснення стало швидшим, а час кліку лишився в межах шуму. Цей сценарій окремо позначено INCONCLUSIVE для загальної затримки.

Дві початкові пари відхилено через зміну камери або втрачений клік, одну через таймаут GUI. Для кожної виконано повтор A/B з тим самим порядком. Відхилені журнали збережено в каталогах з префіксом `rejected-`.

У всіх 33 прийнятих GUI-парах збіглися початковий стан, порядок цілей, payload, призначення і причини для всіх цілей, вартість, готовий залишок, черги, перша хвиля, RNG і NetHash до та після застосування й після 105 кроків. При нульовому запасі обидва варіанти зберігають чернетку без пуску.

## Детермінізм і HUD

В 11 додаткових парах результат збігся для видалення цілі, скорочення запасу безпосередньо перед кліком, недоступної цілі, зміни стану та власника установки, рівноцінних установок, змішаного й відкладеного ударів, повторного кліку, локального хоста, зміни запасу до застосування команди хостом та GUI HUD.

- У SP і на хості після зняття 80 ракет у чергу поставлено 420. Хост застосував команду в turn 0 до першого симуляційного кроку. Повторне підтвердження не продублювало команду, а команда від недійсного відправника не змінила стан. Перша хвиля з'явилась на 92-му кроці. NetHash після 105 кроків збігся з A в обох сценаріях (`16dcd20153b93032` для SP, `97c543ae77491996` для хоста).
- Реальний GUI fixture з 200 цілями підтвердив скасування без витрати боєзапасу, відновлення чернетки, зміну зброї та ru/uk/en, масштаб і viewport, а також розподіл вводу між картою, підтвердженням і Settings.
- Ідентичність гри `0.36.1`, `PROTO=7`, `SIM_REV=v036-integration-1`, `Save.FORMAT=1`. Очікувані хеші наявних тестів збережено.

## Контроль достатнього боєзапасу

Для 500/500 три GUI-пари дали різноспрямовану різницю. Медіана підтвердження 18,34 → 20,48 мс. Вплив на загальну GUI-затримку за повного запасу лишається INCONCLUSIVE.

Окремо в п'яти чергованих headless-парах виконано по 96 планувань того самого списку після восьми прогрівальних викликів. Той самий official runtime, affinity CPU 4–7, час головного потоку з `/proc/thread-self/stat` і `CLK_TCK=100`. Медіана CPU 12,917 → 12,917 мс за виклик. Цей контроль не показав деградації CPU планувальника. Сирі заміри є в `full-stock-cpu.log` та `full-cpu-*/result.json`.
