# R01 — план оптимізації

## P0 · 2–3 FPS / 333–500 мс

Спершу отримати копію справжнього SP-збереження перед просіданням та відтворювану послідовність дій, позицію камери, налаштування і швидкість. Взяти кілька 10–20-секундних вибірок baseline з двома повторами та коротку пару з нижчою роздільністю. Run D уже приймає копію штатного FORMAT 1 save. Фіксований replay підходить для однакових умов. Для симптомів, залежних від швидкості чи наявних світових jobs, додатково прогнати штатний SP delta з `--adaptive`. Зібрати ETW/WPA або інший доступний CPU/GPU trace на native Windows з frame/present events, sampling stacks та wait attribution. На фазі збору зміни gameplay не потрібні. Складність середня.

Пріоритет виправлення визначати за атрибуцією кадрів ≥333 мс:

- Якщо домінує main/worker wait, окремо заміряти queue age, scheduler delay, execution і commit stalls для roads/enclaves/rail/supply. У MP зберегти детерміновані eligibility tick, порядок commit і застосовані дані. У proof-of-concept змінювати лише підтверджений job path, оцінка середня або висока. Перевірка включає фіксовані команди та same-seed hashes, повторне restore і два peers з різними швидкостями CPU.
- Якщо домінує бойова симуляція, додати лічильники кандидатів та часу `ArmyFire._spot/_impact`, late route jobs і `Defense._targets`. Розглянути просторову фільтрацію підтвердженого повного перебору зі збереженням порядку списків, tie-break, ownership і RNG draws. Для impacts індекс має бути актуальним на тому самому тикові. Потрібні characterization tests для дальності, руйнування мостів, знищення/переміщення цілей і повторної ініціалізації після load. Оцінка середня/висока. Порівнювати D з реального snapshot і C для наземного захисту від регресій.
- Якщо домінує render або present, відділити CPU draw preparation, render thread, upload, GPU passes і present wait. Оптимізувати лише виміряний шар, з перевіркою картинки, zoom/fog/night, dtype буферів і FPS на однаковій камері. Оцінка залежить від trace. Синхронний GPU/OS stall поза грою потребує окремого середовищного repro.

Критерій приймання майбутнього P0 — зменшення кількості кадрів ≥333 мс і p95/p99 у відтвореній сцені з тим самим станом і діями. Для тривалого 2–3 FPS порівнювати сталу ділянку, окремо від завантаження і поодиноких стрибків.

## P1 · Найближчий вузький PoC

**Перша конкретна зміна — повторне використання тимчасових масивів і texture buckets у `UnitsLayer._ground_units`.** У C шлях `UnitsLayer._draw` коштував 1,14 мс на кадр у середньому. Джерело містить три нові масиви метаданих, dictionary та buckets за texture RID на draw. Спочатку розділити draw timing на `_ground_units` і решту та звірити кількість видимих юнітів. У PoC зберегти чинний порядок заповнення RID, тіней, спрайтів і overlays, reuse лише всередині конкретного UnitsLayer, очищати refs і записи після зменшення видимого набору або зміни світу. Оцінка мала/середня. Втручання суто visual, ризик для Save/MP низький за відсутності записів у GameWorld або Unit.

Перед/після — два черговані повтори C на 1280×720, як з cap, так і uncapped із зафіксованою камерою, A для контролю й D для snapshot restore. Порівняти `UnitsLayer._draw/_ground_units`, загальні p50/p95/p99, draws, RSS і перші/останні NetHash на однаковому workload. Перевірити selection, fog, тіні, навігацію камери й нічні проходи. Варіація SP job completion вимагає позначати пари з різними станами. Очікуваний механізм — менше короткоживучих GDScript containers, обсяг виграшу потребує вимірювання.

Другий кандидат — 13–15 мс для пачки `Army.order_attack`; більшу частину в C вже атрибутовано в `nav_path`. Спочатку записати route count, cache hit/miss, topology/version і час A*, далі перевірити reuse лише для еквівалентних запитів. Параметри ключа, версія nav, порядок шляхів і семантика fallback мають зберегтися. Оцінка середня. Перед/після — C з ідентичною пачкою наказів, тест порушеного/відновленого моста, same-seed replay із Save/Load та lockstep.

## P2 · Після підтвердження локальної вартості

- Узгодити dirty-region updates у terrain/territory і скорочення uploads, якщо `frame.terrain_territory` зростає в D. Оцінка середня, ризик для gameplay низький лише за збереження authoritative map та порядку cues. Порівняти p95 кадрів із серією build/capture, повні текстури і state hashes.
- Дрібні allocations у візуальних VFX або UI скорочувати лише за даними allocation trace. Оцінка мала. Візуальний тест ефектів, відсутність утриманих refs і той самий контрольний benchmark.
- Якщо генерація і shader warmup впливають на початок тесту, окремо вести cold startup, стабільний прогін і перший прогін після завантаження. Сценарії порівнювати за workload, роздільністю, build і ROI. Історичні CPU headless числа залишаються окремим baseline.
