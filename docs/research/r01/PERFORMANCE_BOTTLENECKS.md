## Що доведено в короткому наземному бою

Медіана повного кадру близько 16,67 мс при cap 60. У C найважчою виміряною системою симуляції є Army. Найдорожчий виміряний GDScript шлях відображення — малювання UnitsLayer. Це доведено для двох порівнюваних запусків C на 1280×720. Причина катастрофічного late-game просідання лишається невстановленою.

| Ранг за середнім у C | Підсистема | Основний код | C1 / C3, мс wall на кадр |
| --- | --- | --- | --- |
| 1 | Наземні війська | `game/game/army.gd:458`, `Army.update` | 1.423 / 1.440 |
| 2 | Малювання військ і бойових об'єктів | `game/world/units_layer.gd:202`, `UnitsLayer._draw` | 1.141 / 1.137 |
| 3 | Розширення територій | `game/game/game_world/gw_map.gd`, `_expand_tick` | 0.366 / 0.358 |
| 4 | Підготовка малювання військ | `game/world/units_layer.gd:94`, `UnitsLayer._process` | 0.313 / 0.311 |
| 5 | Публікація terrain/territory та checkpoints | `game/game/game_world.gd:453`, хвіст `_process` | 0.160 / 0.157 |

На C1/C3 Army p99 становив 6,03/6,98 мс, максимум 8,01/8,42 мс. Усередині Army рух коштував 0,333/0,337 мс у середньому, acquisition — 0,096/0,096 мс з p99 2,40/2,30, ракети — 0,117/0,118 мс з p99 2,13/1,99. AI update близько 0,050–0,051 мс на кадр, p99 1,13–1,20. Контрольна пара наказів коштувала 13,14/15,37 мс одноразово, з них заміряний `nav_path` 8,84/9,86 мс. Саме на кадрі наказів C1/C3 отримано 26,71/28,90 мс, із яких охоплені непересічні GDScript scopes тривали 19,50/22,05 мс. Це підтверджує джерело звичайного короткого стрибка, а не 2–3 FPS.

Час навігації, пошуку цілей, руху й снарядів усередині Army зберігається як вкладені інтервали. Час Army уже містить ці виклики, тому їх не додаємо до Army. `sim.*` приблизні інтервали між наявними межами `_pf`. Незамерені короткі виклики між маркерами потрапляють у сусідню групу. Самостійний інтервал `frame.sim_step` вимірює весь виклик.

## Непояснені довгі кадри

Окремі повільні кадри виникали й у A. Дані не дають ототожнити frame pacing/compositor, витіснення потоку, інший GDScript, команди драйверу або конкуренцію worker. Порівнювати viewport GPU timing із сумою інших інтервалів як «залишком кадру» некоректно. GPU query може мати іншу затримку, а CPU/GPU та worker робота перекриваються. Рівень доступу Linux `perf_event_paranoid=4` заблокував task-clock/context switches. RSS і CPU процесу з `/proc` збережено, та вони не локалізують причину стрибка алокацій і не є Windows profiler trace.

Найдовший зафіксований кадр становив 196,04 мс у C2. Кінцевий розмір вікна виявився 1853×1011, тому C2 поза основною парою. На цьому кадрі непересічні GDScript scopes охопили 3,47 мс, з яких `_sim_step` — 1,42 мс. У A1 кадр 100,34 мс охоплено на 0,57 мс, у D2 кадр 99,15 мс — на 1,20 мс. Кадр C uncapped у 81,16 мс мав 2,75 мс охопленого часу. У цих прикладах дані не атрибутують основну частину stall.

У керованому C root viewport GPU p95 0,33/0,55 мс, root viewport render CPU p95 0,93/0,98 мс. Перехід 1280×720 → 960×540 на 60 cap дав 16,66 → 16,67 мс медіани й 0,33 → 0,34 мс GPU p95 для C1 й C-low з однаковими start/end hashes. Тут немає доказу постійного GPU saturation. Цей висновок обмежено наземною сценою, поточними render settings і точністю root viewport timing. Triple-buffer/present, driver stalls і справжній пізній бій з авіацією/ППО залишаються відкритими.
